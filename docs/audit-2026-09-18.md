# Production Engineering Loop audit — 2026-09-18

**Verdict:** A coherent, locally installable engineering skill exists. The broader proposition—an end-to-end plugin for arbitrary coding tools that demonstrably saves tokens and improves shipped code—is not established. It is worth piloting for explicit feature contracts, continuity, and evidence-based handoffs. It is not ready to market on measured efficiency, universal compatibility, compliance, or defect-free output.

Reviewed version: skill metadata **0.3.0**. The repository had an uncommitted `main` worktree, no commits, and no configured Git remote. [Source fingerprints](../evals/audit-2026-09-18/reviewed-source-sha256.json) identify the inspected files. This audit adds evidence and this report; it does not change the skill, its templates, or its release configuration.

The [Agent Skills specification](https://agentskills.io/specification) defines the standalone directory format. Neither format by itself proves engineering quality.

## Evidence collected

### Packaging and repository checks

These commands passed locally:

```sh
python3 scripts/validate.py
python3 -m unittest discover -s tests -v
```

The locally available skill-creator `quick_validate.py` also passed against `skills/production-engineering-loop`. The eight repository tests exercise package validation, not feature-building behavior. The current GitHub Actions workflow runs those packaging checks; it does not run agent evaluations, and no hosted CI execution was verified.

The local installation pilot compared package bytes after copying through Skills CLI. A local copy install is useful evidence but leaves public distribution and actual host activation untested.

### Fresh-session continuation versus a baseline

The [retained pilot](../evals/audit-2026-09-18/README.md) used identical source, README, and four initial tests. The skill condition additionally received saved project/feature memory from an earlier task, deliberately made stale by renaming `inventory.py` to `stock.py`. Both fresh agents received the same atomic batch-adjustment request.

| Observation | Skill plus saved memory | No-skill baseline |
| --- | --- | --- |
| Final repository tests | 11 passed | 11 passed |
| Independent contract cases | 7,422 passed | 7,422 passed |
| Correct atomic rollback and error order | Verified within enumerated domain | Verified within enumerated domain |
| Recovered stale memory locations | Observed | No saved memory provided |
| Updated repository context and handoff | Observed | Not requested in baseline |
| Actual token cost and elapsed comparison | Unavailable | Unavailable |

The independent evaluator was prepared before implementation outputs and rejected a deliberately non-atomic negative control. This strengthens the correctness evidence. The 7,422 cases are combinations over one small bounded domain, not 7,422 independent development tasks.

The skill agent staged touched products; the baseline copied the entire stock dictionary. Both satisfy the contract. No workload or performance benchmark was defined, so this implementation difference is not evidence of measured efficiency or a general causal benefit from the skill.

One pair cannot estimate reliability or superiority. It also combines skill instructions with memory availability. Add a memory-only baseline to separate those effects. Exact model-version metadata and token telemetry were unavailable. Completed outputs can be rechecked from the retained bundle; reproducing agent behavior requires new, potentially different runs.

## Material gaps, in priority order

### 1. The main efficiency claim has no measurement

**Location:** [SKILL.md](../skills/production-engineering-loop/SKILL.md), [task-context.md](../skills/production-engineering-loop/references/task-context.md), and the current evaluations.

Path/symbol maps can focus retrieval, but savings must exceed the cost of loading the skill, reading memory, checking its freshness, and updating it. The skill entrypoint, project-learning reference, task-context reference, feature-evaluations reference, and full feature template total approximately **5,505 words / 40,026 bytes**. This is an illustrative feature-work route, not a guaranteed per-run load and not a token count. Additional risk-specific references can add context; selective reading can reduce it.

The earlier fixture maintained a 191-line feature record for a six-line function. This continuation expanded that record to 252 lines. Much of it is legitimate contract and historical evidence, but storing and rereading it has a cost. Progressive disclosure helps only if the agent actually retrieves the relevant sections. The [OpenAI skills guide](https://learn.chatgpt.com/docs/build-skills) describes this selective-loading approach; implementation and measurement still matter.

**Required before claiming savings:** paired measurements of total input/output tokens, cached tokens where exposed, context reads, completion quality, and documentation maintenance across initial adoption and repeated tasks. Report the one-time onboarding cost separately and calculate net cost over a sequence of features. Fewer searches or smaller diffs alone are insufficient.

### 2. Behavioral evidence is narrow

**Location:** [learning-loop-result.md](../evals/learning-loop-result.md), [feature-context-result.md](../evals/feature-context-result.md), and this pilot.

The new pilot closes part of the missing fresh-session evidence: retained knowledge was used and stale locations were repaired. It does not validate long-term memory quality, conflicting lessons, changed dependencies, cross-branch contamination, or complex project retrieval. The independent baseline also met the contract, so a claim of improved code quality would exceed the evidence.

**Next evidence:** multiple representative repositories and held-out tasks, repeated runs, and a baseline with identical repository memory. Include a refactor, changed public contract, failure-path integration, stale command, and misleading lesson. Measure material defects, unauthorized scope changes, acceptance completion, and human correction effort. Use acceptance checks prepared independently of agent outputs. Keep expensive or destructive scenarios isolated.

### 3. Documentation proportionality needs a demonstrated operating mode

**Location:** [SKILL.md](../skills/production-engineering-loop/SKILL.md), especially the adjacent small-fix and full-feature-contract instructions; [feature-template.md](../skills/production-engineering-loop/assets/feature-template.md).

The skill already says small fixes need only a short statement and records should be reused. It also directs meaningful changes through a 227-line template. The toy evaluations show that an agent can still choose substantial paperwork. This is a concrete adoption and context-cost concern, not evidence that the user's comprehensive template is wrong.

**Recommended change after review:** retain the complete PRI template for substantial work and add an explicit compact execution mode for small related changes. Keep current paths, next step, essential criteria, and commands easy to retrieve without replaying historical evidence. Demonstrate both modes and measure whether detail is preserved where it matters. Do not delete the user's sections by default.

### 4. Distribution and native compatibility remain unfinished

**Location:** [README.md](../README.md), [installation.md](installation.md), [publishing.md](publishing.md), and absence of a plugin manifest.

The repository supports a portable skill distribution strategy. It is not yet a published, tested plugin product. There is no verified public URL to install, and native host discovery has not been smoke-tested. A manifest would complete packaging for a chosen plugin ecosystem, but cannot establish universal host support.

**Required before public compatibility claims:** publish a versioned source snapshot, replace the owner placeholder, verify installation from that source, and maintain a host/version matrix separating install, discovery, explicit invocation, and behavior. Add plugin packaging only for the ecosystems being claimed. A valid standalone skill can be released without pretending to be a plugin.

### 5. Evidence retention and ongoing evaluation need integration

**Location:** [.github/workflows/validate.yml](../.github/workflows/validate.yml) and the evaluation records.

Historical evaluations mainly summarize outcomes. This audit now retains starting fixtures, finished artifacts, diffs, source fingerprints, a separate acceptance checker, and actual final command output. That improves inspectability. It does not retain every original agent interaction, the intermediate red scaffold, exact model metadata, or an archived skill source snapshot.

**Next step:** commit/archive the reviewed release source, retain evaluation configurations, and make bounded deterministic fixture checks available in CI. Rerun actual agent evaluations for meaningful workflow changes; replaying old finished fixtures alone cannot detect whether a changed skill causes new agents to behave worse.

## Standards assessment

The most defensible statement is **partial alignment with secure-development practices**. As a concrete reference, [NIST SSDF 1.1](https://csrc.nist.gov/pubs/sp/800/218/final) and its [practice definitions](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-218.pdf) support the following limited mapping:

| SSDF practice | Related skill behavior | Remaining limit |
| --- | --- | --- |
| PO.1: security requirements | Feature contracts, trust boundaries, invariants | Does not establish organizational requirements or governance. |
| PW.7: code review/analysis | Risk-based implementation review | Tool execution and reviewer competence remain environment-dependent. |
| PW.8: executable testing | Failure-path checks and recorded outcomes | Cannot guarantee appropriate coverage or enforce hosted gates. |
| RV.3: recurrence prevention | Scoped lessons and regression checks | No verified organization-wide vulnerability process or long-term outcome data. |

These are relationships between instructions and practices, not a compliance assessment. Authentication, migration, release integrity, and operational controls still require project-specific implementations and evidence. No OWASP, ISO, SOC 2, or other certification was assessed.

## Does it have significance?

**Yes, as a reusable workflow whose benefits remain to be measured.** Its clearest distinctive combination is the user's detailed contract, a current path/symbol map, acceptance-to-evidence mapping, explicit next-step continuity, and narrowly scoped repository lessons. That can make resumed feature work easier to inspect and reduce ambiguity between sessions. The continuation pilot shows this mechanism can work.

**Its advantage is weakest on small, obvious tasks.** A capable baseline already solved this example correctly. Generic instructions to test, review, and write clean code are not a strong differentiator, and a large contract can cost more than rediscovering a tiny module. Existing well-maintained architecture documents and development gates may already provide much of the value.

The learning mechanism is external project memory: inspect current evidence, update the map and contract, add an appropriate regression, reuse the knowledge later, and invalidate it when source changes. It does not train model weights or autonomously improve the shared skill. The design correctly limits lessons to demonstrated conditions and prevents silently rewriting the installed instructions.

An honest release description today would be:

> A portable engineering workflow for explicit feature contracts, repository context, regression-first implementation, and evidence-based handoffs. Locally evaluated on small fixtures; efficiency and cross-host behavior remain under evaluation.

A sensible sequence is: demonstrate proportional documentation; measure repeated-task quality and total cost against fair baselines; publish a versioned skill with a verified installation matrix; add native plugin packaging where demanded. Expand runtime tooling only where measurements show that instruction-driven retrieval or memory maintenance is unreliable or expensive.

**Disposition:** suitable for a transparent experimental skill release after distribution setup. Insufficient evidence for a proven token-saving, universally compatible, production-quality automation product. No material package-integrity defect was found in the inspected local checks; that narrower result must not be mistaken for validation of every product claim.
